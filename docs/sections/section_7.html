C++ Crash Course for Python Developers

Before we dive into the trading engine code, we need to learn a few C++ basics. C++ has a reputation for being scary, but underneath, it's just a programming language that asks you to be more specific about what you want.

Variables and Types

Key Difference: In Python, variables can change their type on the fly (Dynamic Typing). In C++, you must declare exactly what a variable holds before you use it, and it can never change (Static Typing).

In Python, you can write:

price = 100.50  # Python figures out this is a float
price = "One Hundred" # Now it's a string!

In C++, you must declare the type upfront:

double price = 100.50; // 'double' means a high-precision decimal number
// price = "One Hundred"; // ERROR! A double cannot become a string.
int shares = 50; // 'int' is a whole number (integer)
std::string symbol = "AAPL"; // 'std::string' is text

Pointers and References

Analogy: Imagine a house.
  • The Variable is the house itself.
  • A Reference (&) is an alternate name for the same house (like calling it "My Home" instead of "The House").
  • A Pointer (*) is a piece of paper with the address of the house written on it.

In Python, when you pass an object to a function, Python quietly passes a reference to it. In C++, you have to be explicit.

int my_money = 1000;

// REFERENCE: 'alias' is literally the same memory spot as 'my_money'
int& alias = my_money; 
alias = 2000; // my_money is now 2000!

// POINTER: 'address' holds the memory location (e.g., 0x7FFA...) of 'my_money'
int* address = &my_money; 
*address = 3000; // Go to the address and change the value. my_money is now 3000!

Why do we use pointers? Because moving a piece of paper (the address) is incredibly fast, whereas moving an entire house (copying massive amounts of data) is slow.

Header Files (.hpp) vs Source Files (.cpp)

Analogy: A Header File (.hpp) is the Restaurant Menu. It tells you what dishes are available, but doesn't tell you how to cook them. A Source File (.cpp) is the Kitchen. It contains the actual recipes and does the cooking.

In Python, you just write code in a .py file. In C++, we split things up so that when different parts of the program want to talk to each other, they only need to look at the menu (.hpp) rather than reading the entire recipe (.cpp).

What is #include?

Beginner Tip: #include is exactly like import in Python.

When you write #include <iostream>, it's like writing import sys in Python. It pulls in code written by someone else so you can use it. #include "MyMenu.hpp" imports your own local files.

Namespaces

Analogy: Namespaces are like last names. If someone says "Hey, John!", and there are three Johns in the room, it's confusing. If they say "Hey, John Smith!", it's clear.

In C++, a lot of standard tools are in the std (standard) namespace. To use the standard string, you say std::string (John from the std family).

Virtual Classes and Interfaces

Analogy: A pure virtual class is a blueprint from a strict city inspector. It says, "If you want to build a house in this city, you must include a front door and a roof." It doesn't build the house for you; it just forces the builder to follow the rules.

In C++, a class with virtual function() = 0; is a "pure virtual class" (also called an Interface). We use this to define a strict set of rules for our trading strategies. Any strategy we write MUST have specific functions, otherwise, the compiler won't let it run.

extern "C" and dlopen()

Analogy: dlopen() is like plugging a USB drive into your computer while it's already running. You don't have to turn off the computer to plug it in; the OS detects it and loads its contents dynamically.

Normally, C++ programs are glued completely together before they start. But we want our python agent to write a new strategy, compile it, and plug it into the running backtester without stopping the engine. We do this using Shared Libraries (.so files on Linux/Mac, .dll on Windows) and the dlopen() function.

However, C++ likes to "mangle" function names (turning my_function into something unreadable like _Z11my_functionv) to handle complex features. extern "C" tells the C++ compiler: "Hey, don't mangle this name. Keep it simple like the C language does, so my program can easily find it when I plug it in later."

StrategyInterface.hpp — The Contract

Now let's look at real code! Our engine needs a strict set of rules that every dynamically loaded strategy must follow. We define these rules in StrategyInterface.hpp.

#pragma once
#include <cstdint>

// --- Data Structures ---

struct Tick {
    uint64_t timestamp;  // When it happened (in nanoseconds)
    double price;        // The price of the asset
    double volume;       // How much was traded
};

struct MarketEvent {
    Tick tick;
    // We can add more info here later, like order book depth
};

struct SignalEvent {
    int signal;          // 1 for BUY, -1 for SELL, 0 for HOLD
    double confidence;   // 0.0 to 1.0
};

struct FillEvent {
    uint64_t timestamp;
    double fill_price;
    double fill_qty;
    double commission;
};

struct StrategyMetrics {
    double total_pnl;
    double win_rate;
    double max_drawdown;
};

These struct blocks are just simple data containers. Think of them like Python @dataclass or dictionaries, but much faster because they take up an exact, predictable amount of memory.

// --- The Interface ---

class StrategyInterface {
public:
    // A virtual destructor is required for safe cleanup
    virtual ~StrategyInterface() = default;

    // The core function: given a market event, what is your signal?
    virtual SignalEvent on_market_event(const MarketEvent& event) = 0;

    // Called when an order is executed
    virtual void on_fill(const FillEvent& event) = 0;

    // Request the strategy's current internal metrics
    virtual StrategyMetrics get_metrics() const = 0;
};

// --- The USB Plug ---
// This is the function that the engine will look for when loading the .so file
extern "C" StrategyInterface* create_strategy();
extern "C" void destroy_strategy(StrategyInterface* strategy);

Why this design? This is the Plugin Architecture. The engine doesn't care if the strategy uses moving averages, neural networks, or a magic 8-ball. All the engine cares about is that it can call on_market_event() and get back a SignalEvent. The create_strategy() function wrapped in extern "C" is the exact hook the engine searches for when it uses dlopen() to plug the strategy in.

ColumnarTickStore — Zero-Copy Data Access

When you have 10 years of tick data (millions of rows), how do you read it fast? Python's pandas is okay, but it copies data into memory. We want Zero-Copy.

Row-oriented vs Column-oriented storage

Analogy: Imagine a spreadsheet of employees with columns: [Name, Age, Department].
  • Row-oriented: Reading row by row (John, 30, HR -> Jane, 45, IT). If you only want to find the average Age, you still have to step over all the Names and Departments.
  • Column-oriented: The data is stored in columns (John, Jane) (30, 45) (HR, IT). If you want the average age, you just grab the (30, 45) chunk. It's incredibly fast!

What is memory mapping (mmap)?

mmap is an operating system trick. Instead of reading a file from the hard drive into RAM (which takes time), mmap tricks the CPU into thinking the hard drive file is in RAM. As your program accesses variables, the OS secretly fetches chunks of the file in the background. No loading screens, no copying!
Let's look at the C++ code that does this: 
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>

class ColumnarTickStore {
private:
    double* prices_array;
    size_t num_ticks;
    int file_descriptor;

public:
    ColumnarTickStore(const char* filepath) {
        // 1. Open the file directly
        file_descriptor = open(filepath, O_RDONLY);
        
        // 2. Figure out how big it is
        size_t file_size = lseek(file_descriptor, 0, SEEK_END);
        num_ticks = file_size / sizeof(double);
        
        // 3. mmap: Map the file directly into memory space!
        prices_array = (double*) mmap(
            nullptr,              // Let the OS pick the memory address
            file_size,            // Size of the file
            PROT_READ,            // We only want to read, not write
            MAP_SHARED,           // Share this mapping
            file_descriptor,      // The file we opened
            0                     // Start at the beginning
        );
    }
    
    // Get a price instantly, as if it was a normal array in RAM
    inline double get_price(size_t index) const {
        return prices_array[index];
    }
};

What is prefetching?

Analogy: You are eating at a multi-course dinner. Prefetching is the waiter noticing you are almost done with your soup, and bringing the main course out so it's sitting next to you exactly when you finish the soup. No waiting!

In C++, we can tell the CPU: "Hey, I'm currently looking at tick 1,000. In a microsecond, I'm going to need tick 1,010. Go fetch it from RAM into your ultra-fast L1 cache right now." We do this using __builtin_prefetch(&prices_array[index + 10]);.

BacktestEngine — The Main Event Loop

The BacktestEngine is the heart of the C++ worker. It loops through all the historical data, feeds it to the strategy, and records the results.

#include <dlfcn.h> // For dlopen

class BacktestEngine {
    void run(const std::string& strategy_so_path) {
        // 1. Plug in the strategy using dlopen
        void* handle = dlopen(strategy_so_path.c_str(), RTLD_NOW);
        
        // 2. Find the "create_strategy" function
        auto create_func = (StrategyInterface* (*)()) dlsym(handle, "create_strategy");
        
        // 3. Create the strategy object
        StrategyInterface* strategy = create_func();
        
        // 4. Batch Processing Loop
        const size_t BATCH_SIZE = 4096;
        for (size_t i = 0; i < total_ticks; i += BATCH_SIZE) {
            
            for (size_t j = 0; j < BATCH_SIZE; ++j) {
                size_t idx = i + j;
                if (idx >= total_ticks) break;

                // Create the event
                MarketEvent event;
                event.tick.price = tick_store.get_price(idx);
                
                // Prefetch future data to speed up memory access
                __builtin_prefetch(&tick_store.get_price(idx + 16), 0, 1);

                // 5. Ask the strategy for a decision
                SignalEvent signal = strategy->on_market_event(event);
                
                // 6. Execute the decision in the simulator
                simulator.process_signals(signal, event.tick);
            }
        }
    }
};

Why batches of 4096? CPUs love patterns and predictable chunks. A batch of 4096 fits perfectly into most CPU caches. If we process one by one entirely, we might interrupt the CPU's rhythm. By processing in chunks, the CPU can optimize its pipeline.

Latency Sampling: We occasionally measure how long it takes to process a tick. Why not measure every tick? Because checking the clock (calling time functions) takes time! If you measure every tick, the act of measuring actually slows down the engine. We only sample every 1,000th tick to keep things fast.

OrderMatchingSimulator — Realistic Trade Execution

When our strategy says "BUY", we don't just magically get the stock for free. A backtester is useless if it's not realistic. The OrderMatchingSimulator applies real-world physics to our trades.

Slippage: Imagine ordering a TV online for $500, but by the time you click "Checkout", the price jumps to $505. That $5 difference is slippage. In fast markets, by the time your order reaches the exchange, the price has moved.

Commission: The fee the broker charges you for doing the trade (e.g., $0.001 per share).

Market vs Limit Orders:

  • Market Order: "Buy this stock right now, whatever the price is!" (Guarantees execution, subject to heavy slippage).
  • Limit Order: "Only buy this stock if the price is $100 or less." (Guarantees price, but might never execute if the price doesn't drop).
void process_signals(const SignalEvent& signal, const Tick& tick) {
    if (signal.signal == 1) { // BUY
        // Calculate realistic fill price (simulating slippage)
        // We add a tiny bit (0.01%) to the price to simulate getting a bad fill
        double slippage_penalty = tick.price * 0.0001; 
        double fill_price = tick.price + slippage_penalty;
        
        // Calculate broker fee
        double commission = 0.50; // Flat fee per trade
        
        // Execute!
        portfolio_cash -= (fill_price * 100) + commission; // Bought 100 shares
        positions += 100;
        
        // Tell the strategy it was filled
        FillEvent fill{tick.timestamp, fill_price, 100.0, commission};
        strategy->on_fill(fill);
    }
}

SimdMetrics — SIMD Acceleration

To calculate things like Variance or Moving Averages across millions of data points, standard loops are too slow. We use SIMD (Single Instruction, Multiple Data).

Analogy: Standard C++ loop is like a checkout lane at a grocery store. The cashier scans one item at a time (Apple, then Banana, then Orange).
SIMD is like a super-cashier with 4 arms who grabs 4 items and scans them all at the exact same millisecond.

Modern Intel/AMD CPUs have a feature called AVX2. This gives the CPU massive 256-bit registers. Since a standard double decimal number is 64 bits long, 256 / 64 = 4. We can cram 4 numbers into one register and do math on all 4 simultaneously!

Let's look at how we sum up an array incredibly fast using SIMD C++ intrinsics:

#include <immintrin.h> // The AVX2 header

double sum_avx2(const double* data, size_t length) {
    // 1. Create a 256-bit register initialized to all zeros. [0.0, 0.0, 0.0, 0.0]
    __m256d sum_vec = _mm256_setzero_pd();
    
    size_t i = 0;
    // 2. Loop in chunks of 4!
    for (; i + 3 < length; i += 4) {
        // Load 4 numbers from our array directly into a 256-bit register
        __m256d data_vec = _mm256_loadu_pd(&data[i]);
        
        // ADD all 4 numbers to our sum_vec simultaneously in one CPU cycle
        sum_vec = _mm256_add_pd(sum_vec, data_vec);
    }
    
    // 3. We now have 4 separate totals. We need to add them together.
    double temp[4];
    _mm256_storeu_pd(temp, sum_vec);
    double total_sum = temp[0] + temp[1] + temp[2] + temp[3];
    
    // 4. The Scalar Fallback: What if the array length wasn't a perfect multiple of 4?
    // E.g., length 10. SIMD does 8. We do the last 2 the normal, slow way.
    for (; i < length; ++i) {
        total_sum += data[i];
    }
    
    return total_sum;
}

What is _mm256_fmadd_pd?

When calculating Variance, the math is roughly (price - mean)^2. You have to multiply, and then add. CPUs have a special hardware circuit called Fused Multiply-Add (FMA). The instruction _mm256_fmadd_pd(a, b, c) calculates (a * b) + c in a single lightning-fast step, avoiding rounding errors.

CMakeLists.txt — The Build System

Finally, how do we turn all this C++ text into an executable program? Python just runs via the Python interpreter. C++ must be compiled.

Analogy: CMake is the recipe for building your project. It tells the kitchen (the compiler) exactly which files to compile, what folders to look in, and what compiler flags (optimizations) to turn on. 
# 1. Require a modern version of CMake
cmake_minimum_required(VERSION 3.10)

# 2. Name our project
project(BacktestEngine)

# 3. Use C++17 standard (modern C++)
set(CMAKE_CXX_STANDARD 17)

# 4. Compiler Flags: Turn on MAX SPEED!
# -O3 tells the compiler to optimize the code as heavily as possible.
# -mavx2 and -mfma tell the compiler "This CPU supports AVX2 and Fused-Multiply-Add, use them!"
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -O3 -mavx2 -mfma -Wall")

# 5. Build our Main Executable Engine from our source files
add_executable(engine 
    src/main.cpp 
    src/BacktestEngine.cpp
)

# 6. Link dynamic loading library (-ldl) so dlopen() works
target_link_libraries(engine dl)
