Section 16: SDE Interview Questions & Answers

If you put this project on your resume, recruiters and engineering managers will definitely ask you about it. This project touches on many advanced topics that are perfect for technical interviews. Here is a curated list of Software Development Engineer (SDE) interview questions you might face, along with detailed, beginner-friendly answers.

1. Systems Design: "How would you scale this system if we wanted to run 10,000 backtests per minute?"

What they are looking for: Do you understand bottlenecks, horizontal scaling, and message queues?

How to answer:

  • The Bottleneck: The C++ worker is fast, but compiling the code and spinning up Docker containers takes a few seconds. A single machine can only run so many Docker containers before running out of CPU/Memory.
  • The Solution (Horizontal Scaling): Because we use RabbitMQ, the architecture is already fully decoupled. To scale to 10,000 backtests per minute, we just need to add more consumer machines (EC2 instances).
  • The Details:
    • Deploy an Auto-Scaling Group (ASG) in AWS.
    • The ASG monitors the length of the backtest_tasks RabbitMQ queue.
    • If the queue length grows beyond a certain threshold, the ASG spins up more EC2 instances running the Python consumer.
    • Because RabbitMQ uses prefetch_count=1, tasks are distributed fairly to whichever worker is free.
    • Database Scaling: MongoDB can handle the results, but if write throughput becomes an issue, we can shard the MongoDB cluster based on the task_id.

2. C++ & Performance: "Why did you choose Structure-of-Arrays (SoA) over Array-of-Structures (AoS) for tick data?"

What they are looking for: Do you understand memory layout, CPU caches, and low-level performance optimization?

How to answer:

  • In an Array-of-Structures (AoS), a Tick looks like [{timestamp, bid, ask, last, volume}, {timestamp, bid, ask...}]. If my strategy only needs to calculate the moving average of the last price, the CPU has to load the entire struct into the L1 cache, wasting cache space on bids, asks, and volumes that I'm not using.
  • In a Structure-of-Arrays (SoA), memory is laid out as [last, last, last...], [bid, bid, bid...].
  • Cache Utilization: When I iterate through the last prices, I access contiguous memory addresses. The CPU brings in a full cache line (usually 64 bytes, or 8 double values). With SoA, 100% of that cache line is useful data. With AoS, maybe only 20% of the cache line is useful.
  • SIMD Compatibility: SoA makes it trivial to load data into vector registers (like AVX2) because the data is already packed contiguously.

3. Distributed Systems: "How do you handle a scenario where two orchestrator nodes try to update the same task state at the same time?"

What they are looking for: Do you understand race conditions, locking vs lock-free design, and eventual consistency?

How to answer:

  • We use CRDTs (Conflict-Free Replicated Data Types) backed by Redis to prevent data loss without using expensive distributed locks.
  • If two nodes update the strategy code at the exact same time, we use an LWWRegister (Last-Writer-Wins). The update with the highest UNIX timestamp wins. If the timestamps are perfectly identical, we fallback to a deterministic tie-breaker (comparing the node_id strings lexicographically).
  • For the agent logs, we use an ORSet (Observed-Remove Set). Since each log entry is assigned a unique UUID, if two nodes add logs simultaneously, they just merge their sets together via a mathematical union. No logs are ever lost.

4. Security: "How do you safely execute arbitrary C++ code generated by an AI?"

This is like asking a stranger to cook in your kitchen. You don't want them touching your safe, using your phone, or burning the house down.

How to answer:

We use a multi-layered defense-in-depth approach:

  1. Network Isolation: The Docker container is launched with --network none. If the AI writes a script to download malware or exfiltrate our database passwords, the network request will simply fail.
  2. Resource Limits: The AI could accidentally write an infinite loop. We pass nano_cpus=0.5e9 (half a core) and mem_limit="512m" to Docker so it can't crash the host server. We also enforce a strict 5-second timeout using container.wait(timeout=5).
  3. Privilege Drop: The container runs as a non-root user (sandbox, UID 1000).
  4. Filesystem Restrictions: The strategy library and datasets are mounted as read-only (:ro). The container cannot modify historical data or corrupt the system.

5. AI & Prompt Engineering: "LLMs are notoriously bad at outputting perfect JSON. How does your system handle parsing failures?"

Never assume an external API (especially an AI) will return exactly what you want. Always write defensive code.

How to answer:

  • In the Researcher node, we instruct the LLM to output a JSON string matching the StrategyHypothesis schema.
  • We wrap the parsing in a try-except block.
  • Fallback Strategy: If json.loads() raises a JSONDecodeError, we don't crash the graph. Instead, we take the raw text response, treat the whole thing as the "description", and assign fallback defaults for the name and symbols (e.g. "Generated Strategy" trading "SPY").
  • This allows the pipeline to continue seamlessly to the Coder node, which can usually still understand the raw text perfectly fine.

6. Message Brokers: "Why use RabbitMQ instead of just making an HTTP POST request to the worker?"

What they are looking for: Synchronous vs Asynchronous communication, coupling, and fault tolerance.

How to answer:

  • Timeouts: A backtest can take time (compiling C++ takes a few seconds). HTTP connections can time out if they are held open too long.
  • Fault Tolerance: If the worker crashes midway through an HTTP request, the task is lost. With RabbitMQ, the message stays in the queue until the worker explicitly sends an ACK (acknowledgement). If the worker dies, the message is un-acked and safely re-queued for another worker.
  • Load Balancing: If I have 10 workers, I don't want to build a custom load balancer to figure out which worker is free. RabbitMQ handles this out-of-the-box using prefetch_count=1. The broker automatically routes tasks to workers that aren't busy.

7. C++ Compilation: "Why do you compile the AI-generated strategy into a shared library (.so) instead of an executable?"

What they are looking for: Do you understand dynamic linking, dlopen, and software architecture?

How to answer:

  • The backtesting engine (which contains the Arrow tick reader, order matching simulator, and metrics calculator) is large and complex. If we compiled it into an executable every single time, it would take a long time to build.
  • Instead, we compile the engine ONCE. We expose a stable contract (StrategyInterface.hpp).
  • When the AI writes a strategy, we only compile that tiny file into a shared library (.so). This takes milliseconds.
  • At runtime, the main engine uses dlopen() to load the .so file into its memory space, looks up the create_strategy() function, and executes it at native C++ speeds. This gives us the flexibility of a scripting language (like Python) but the execution speed of compiled C++.
