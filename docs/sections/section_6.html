SECTION 6: The Message Broker & Distributed State — Deep Dive

Welcome to Section 6! In a complex, distributed trading swarm, multiple independent agents (or "bots") are constantly running on different machines or containers. They need a way to reliably talk to each other, share data, and remember past interactions without stepping on each other's toes. This section dives deep into three critical components that make this possible: RabbitMQ (for sending messages), Redis (for memory), and CRDTs (for perfectly synchronized state without a central database).

1. broker/rabbitmq.py - The Communication Backbone

Before we look at the code, let's understand the core technology here: RabbitMQ.

Analogy: A Post Office with Named Mailboxes
Imagine you are writing a letter to a friend. Instead of walking to their house and handing it to them directly (which takes time, and what if they aren't home?), you drop it in a mailbox. The Post Office picks it up, figures out where it needs to go, and holds onto it until your friend is ready to check their mail.

RabbitMQ is exactly this Post Office for our software. When one agent (like an Alpha Generator) finishes a job, it doesn't try to find the Backtester agent directly. It just hands a "message" (a packet of data) to RabbitMQ. RabbitMQ safely holds this message in a line (a queue) until the Backtester is ready to read it.

Key RabbitMQ Vocabulary

  • Exchange: Think of this as the mail sorting center. When a message arrives at the Post Office, it goes to the sorting center first. The exchange looks at the address (the routing key) and decides which local post office (queue) to send it to.
  • Queue: This is the actual mailbox or waiting line where messages sit. An agent connects to a specific queue to read its messages one by one.
  • Routing Key: The address written on the envelope. It tells the exchange exactly where this message belongs.
  • Durable: If the power goes out at the Post Office, do the mailboxes disappear? If a queue is "durable," it means RabbitMQ saves the structure of the queue to disk so it survives a server restart.
  • Persistent: If a queue is durable, the box survives, but what about the letters inside? If a message is marked as "persistent," the message itself is written to disk, ensuring it isn't lost if the server crashes before it is read.

Let's look at the code that sets up our Post Office.


import json
import pika

class SwarmBroker:
    def __init__(self, amqp_url):
        self.params = pika.URLParameters(amqp_url)
        self.conn = pika.BlockingConnection(self.params)
        self.channel = self.conn.channel()

    def declare_topology(self):
        # 1. Create the sorting center
        self.channel.exchange_declare(
            exchange='swarm_tasks',
            exchange_type='direct',
            durable=True
        )

        # 2. Create the mailboxes
        self.channel.queue_declare(queue='task_queue', durable=True)
        self.channel.queue_declare(queue='result_queue', durable=True)

        # 3. Connect the sorting center to the mailboxes
        self.channel.queue_bind(
            exchange='swarm_tasks',
            queue='task_queue',
            routing_key='task.new'
        )
        self.channel.queue_bind(
            exchange='swarm_tasks',
            queue='result_queue',
            routing_key='task.result'
        )

Line-by-Line Walkthrough: declare_topology()

  • self.channel.exchange_declare(...): We create an exchange (sorting center) named swarm_tasks. We use exchange_type='direct', which means "send the message to the queue whose routing key exactly matches the message's routing key." We set durable=True so this sorting center isn't deleted if RabbitMQ restarts.
  • self.channel.queue_declare(...): We create two distinct mailboxes: task_queue (for jobs that need to be done) and result_queue (for jobs that are finished). durable=True ensures the mailboxes survive a crash.
  • self.channel.queue_bind(...): We tell the exchange how to route messages. If a message arrives with the address (routing key) task.new, put it in the task_queue. If it says task.result, put it in the result_queue.

Line-by-Line Walkthrough: publish_task() & publish_result()

  • self.channel.basic_publish(...): This is the function that actually drops the letter in the mailbox.
  • exchange='swarm_tasks': We are handing it to our specific sorting center.
  • routing_key='task.new' or 'task.result': The address on the envelope.
  • body=json.dumps(...): The actual letter! We convert a Python dictionary (the payload) into a JSON string because RabbitMQ only understands raw text/bytes, not Python objects.
  • properties=pika.BasicProperties(delivery_mode=2): This is crucial. delivery_mode=2 tells RabbitMQ to mark this specific message as persistent (save it to disk immediately). If RabbitMQ crashes right after receiving it, the task won't be lost.

The Two Payload Models: What data actually flows here? In publish_task, the payload usually contains instructions: {"task_id": "123", "action": "backtest", "strategy": "RSI_MeanReversion"}. In publish_result, it contains the outcome: {"task_id": "123", "status": "success", "sharpe_ratio": 1.45, "net_profit": 5000}.

2. broker/redis_cache.py - The Agent's Memory

When our Large Language Model (LLM) agents try to write trading code, they usually don't get it right on the first try. They need to try, look at the error, and try again. To do this, they need memory.

Analogy: A Student Studying with Notes
Imagine a student (the LLM) trying to solve a complex math problem. If they have amnesia and forget every previous attempt, they will make the same mistake forever. But if they keep a notebook of their last few attempts ("Okay, method A gave me 5, which is wrong; method B gave me an error"), they can learn and adapt. Redis is this notebook.

Because LLMs charge by the word (token) and have a limited reading capacity (context window), we can't show them every past mistake. We use a Sliding Window.

Analogy: Sliding Window
Think of your phone's text messages. When you look at an ongoing conversation, you usually only care about the last 10 or 20 messages. A sliding window means we only keep the 10 most recent entries; as a new one arrives, the oldest one is pushed out and forgotten.

Here is the exact code that manages this sliding memory using Redis:


import json
from typing import Any
import redis

class AgentMemoryCache:
  def __init__(self, redis_url, window_size=10):
      self._client = redis.from_url(redis_url, decode_responses=True)
      self._window = window_size

  def _key(self, task_id):
      return f"swarm:iterations:{task_id}"

  def append_iteration(self, task_id, entry):
      key = self._key(task_id)
      self._client.rpush(key, json.dumps(entry))
      self._client.ltrim(key, -self._window, -1)
      self._client.expire(key, 86_400)

  def get_history(self, task_id):
      return [json.loads(item) for item in self._client.lrange(self._key(task_id), 0, -1)]

  def format_for_prompt(self, task_id):
      history = self.get_history(task_id)
      if not history: return ""
      lines = ["Previous iterations (most recent last):"]
      for i, entry in enumerate(history, 1):
          lines.append(f"  [{i}] status={entry.get('status')} notes={entry.get('notes', '')[:200]}")
      return "\n".join(lines)

Line-by-Line Walkthrough: AgentMemoryCache

  • def __init__(self, redis_url, window_size=10):
    We initialize our cache. decode_responses=True tells Redis to give us back strings (text) instead of raw bytes, making our lives easier. We set a default memory limit of 10 items.
  • def _key(self, task_id): return f"swarm:iterations:{task_id}"
    Redis is a giant dictionary. We need a unique key to store memory for each specific task. We prefix it with swarm:iterations: to keep things organized.
  • def append_iteration(self, task_id, entry):
    This is how we add a new memory.
  • self._client.rpush(key, json.dumps(entry))
    RPUSH stands for "Right Push". It takes a list in Redis and pushes a new item onto the right (the end) of it. We convert the Python dictionary entry to a JSON string first.
  • self._client.ltrim(key, -self._window, -1)
    LTRIM stands for "List Trim". This is the magic behind the sliding window! We tell Redis: "Trim this list so it ONLY keeps items from index -self._window (e.g., -10, meaning the 10th item from the end) to index -1 (the very last item)." Anything older gets deleted instantly.
  • self._client.expire(key, 86_400)
    We don't want old data clogging up our server forever. We set this memory to expire (delete itself) in 86,400 seconds (exactly 24 hours).
  • def get_history(self, task_id):
    LRANGE gets items from the list. 0 to -1 means "get everything from the first item to the last item." We then use a list comprehension to turn all those JSON strings back into Python dictionaries.
  • def format_for_prompt(self, task_id):
    This is how we feed the memory back to the LLM. The LLM needs plain text, not Python code. We grab the history, and if it's empty, we return an empty string. If we have memory, we loop through it, pulling out the status (e.g., "failed") and the first 200 characters of the notes (e.g., the compiler error message). We join them into a neat text block for the LLM to read.

3. broker/crdt_state.py - CRDTs from Scratch

When you have a swarm of agents running across multiple physical servers (like AWS EC2 instances), they need a way to share data. You could use a central database, but databases can be slow, and if the database goes down, everything stops.

Enter the CRDT (Conflict-free Replicated Data Type).

Analogy: Two People Editing a Google Doc
Imagine you and a friend are editing the same document on Google Docs from different cities. If your internet cuts out for 5 minutes, you can keep typing offline. When your internet comes back, Google Docs magically merges your changes with your friend's changes without breaking the document.

A CRDT is the mathematical rulebook that makes this possible. It allows multiple computers to update their own local copy of a data structure independently, and then later merge their changes seamlessly without needing a central boss to arbitrate conflicts.

The Problem CRDTs Solve

If Node A adds the stock "AAPL" to a set of watched tickers, and Node B simultaneously removes "MSFT", what happens when they sync? A naive system might just overwrite Node B's state with Node A's state, resulting in lost data. CRDTs guarantee Eventual Consistency: no matter what order the messages arrive in, once all nodes have received all messages, they are guaranteed to have the exact same identical state.

Three Types of CRDTs Explained

  • LWWRegister (Last-Writer-Wins Register): Used for simple variables (like a status string). If two nodes update the variable, how do we choose? We attach a timestamp. The one with the later timestamp wins. Concrete example: Node A sets status="running" at 10:01. Node B sets status="failed" at 10:02. When they merge, "failed" wins because 10:02 > 10:01.
  • ORSet (Observed-Remove Set): Used for collections (like a list of active tasks). Why does a simple set break? If Node A adds "Task 1", and Node B simultaneously removes "Task 1", which wins? An ORSet solves this by attaching a unique ID (a tag) to every addition. To remove an item, you say "I am removing the item with tag X". This makes additions and removals distinct events that can't conflict.
  • GCounter (Grow-only Counter): Used for counting things (like total trades made). If you have a simple integer count = 5, and Node A increments it (+1) and Node B increments it (+1), they both broadcast count = 6. When they merge, they see 6 == 6 and the final count is 6, losing a count! A GCounter solves this by giving every node its own personal counter. Node A is {"A": 1}, Node B is {"B": 1}. To get the total, you sum them up: 1 + 1 = 2. If they merge, they take the maximum for each node ID.

Let's look at how we implement this in Python.


import time
import json

class LWWRegister:
    def __init__(self, value=None, timestamp=0):
        self.value = value
        self.timestamp = timestamp

    def update(self, value):
        self.value = value
        self.timestamp = time.time()

    def merge(self, other_register):
        if other_register.timestamp > self.timestamp:
            self.value = other_register.value
            self.timestamp = other_register.timestamp

class SwarmStateCRDT:
    def __init__(self, node_id, pubsub_client):
        self.node_id = node_id
        self.pubsub = pubsub_client
        self.state = {
            "global_status": LWWRegister("idle"),
            "active_agents": LWWRegister(0)
        }

    def update_status(self, new_status):
        self.state["global_status"].update(new_status)
        self.publish_for_sync()

    def publish_for_sync(self):
        # Serialize state and broadcast to other nodes
        payload = {
            "node_id": self.node_id,
            "status_val": self.state["global_status"].value,
            "status_ts": self.state["global_status"].timestamp
        }
        self.pubsub.publish("crdt_sync_channel", json.dumps(payload))

    def subscribe_sync(self, message):
        data = json.loads(message)
        if data["node_id"] == self.node_id:
            return # Ignore our own messages

        incoming_register = LWWRegister(data["status_val"], data["status_ts"])
        self.state["global_status"].merge(incoming_register)

Line-by-Line Walkthrough: SwarmStateCRDT & LWWRegister

  • class LWWRegister:
    This is our Last-Writer-Wins Register.
  • def update(self, value):
    When we update our local value, we record the exact current time time.time().
  • def merge(self, other_register):
    This is the magic CRDT rule. If the incoming data's timestamp is strictly greater than our local timestamp, we overwrite our local value. If ours is newer, we do nothing.
  • class SwarmStateCRDT:
    The manager for our local node's state. It requires a unique node_id (so we know who is talking) and a pubsub_client (like Redis Pub/Sub, so we can shout to the network).
  • def update_status(self, new_status):
    We update our local LWWRegister, and immediately call publish_for_sync() to let the world know.
  • def publish_for_sync(self):
    We package our current value and its timestamp into a JSON dictionary and publish it to the crdt_sync_channel. Every node on the network is listening to this channel.
  • def subscribe_sync(self, message):
    This function runs whenever a message arrives from the network. First, it ignores messages sent by itself (data["node_id"] == self.node_id). Then, it creates a temporary LWWRegister out of the incoming data, and calls the .merge() function. The merge function guarantees that no matter what order these messages arrive in, all nodes will eventually agree on the state with the highest timestamp.

When is CRDT Sync Actually Needed?

If you are running the Swarm on your laptop (a single machine), you don't need CRDTs. A simple local variable or a single Redis server is fine because there is no network latency or node crashes to worry about.

However, in a true production environment (e.g., deploying the Swarm across 5 different AWS EC2 instances in different regions to minimize latency to different stock exchanges), a single central Redis server becomes a bottleneck and a single point of failure. If the Redis server crashes, the whole swarm dies. By using CRDTs, every EC2 instance keeps its own perfectly accurate, local copy of the state. If the network splits and two EC2 instances temporarily lose connection to each other, they continue trading safely, and merge their data flawlessly once the connection is restored.
