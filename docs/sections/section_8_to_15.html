SECTION 8: The Consumer — Docker Sandbox Execution

Welcome to the execution engine of our backtesting swarm! In previous sections, we learned how the orchestrator generates code and schedules tasks. Now, we arrive at the Consumer, the workhorse that actually receives these tasks, compiles the C++ strategies, and runs them safely.

main.py — The Task Consumer

What is a consumer in message queue terms?
In distributed systems, a message queue holds a line of tasks waiting to be done. A consumer is a program that connects to this queue, takes a task, processes it, and then goes back for another one.
Imagine a busy post office. The message queue is the conveyer belt bringing in packages (tasks). The consumer is the mail room worker. The worker picks up one package from the belt, processes it (scans it, weighs it, routes it), and only when they are completely finished do they turn around to pick up the next package. If the post office is really busy, you can just hire more workers (spin up more consumers) to stand at the same conveyer belt!

Walk through main() step by step

Let's look at the core of our consumer loop in main.py:


def main():
    connection = pika.BlockingConnection(pika.ConnectionParameters('rabbitmq'))
    channel = connection.channel()
    
    channel.queue_declare(queue='task_queue', durable=True)
    
    # Fair dispatch
    channel.basic_qos(prefetch_count=1)
    
    channel.basic_consume(queue='task_queue', on_message_callback=callback)
    
    print(' [*] Waiting for messages. To exit press CTRL+C')
    channel.start_consuming()
  • pika.BlockingConnection(...): Pika is the Python library we use to talk to RabbitMQ. This line connects to the RabbitMQ server (hostname 'rabbitmq').
  • channel.queue_declare(queue='task_queue', durable=True): This ensures the queue exists before we try to read from it. durable=True means if RabbitMQ crashes and restarts, our queue (and its messages) will survive.
  • channel.basic_qos(prefetch_count=1): This is a critical setting for performance and stability.
  • channel.basic_consume(...): This tells RabbitMQ, "Hey, whenever a message arrives on 'task_queue', call the function named callback."
  • channel.start_consuming(): This starts an infinite loop, keeping the script alive and constantly listening for new messages.
What is prefetch_count? Why set it to 1?
By default, RabbitMQ might try to push 50 tasks to a consumer all at once to save network trips. But running a C++ backtest takes time and heavy CPU. If one consumer gets 50 heavy tasks while another consumer sits idle, the system is horribly unbalanced. Setting prefetch_count=1 tells RabbitMQ: "Only give me ONE task at a time. Do not give me another one until I have finished and acknowledged the current one." This ensures fair dispatch across your swarm of workers.

The Callback Function and ACK/NACK


def callback(ch, method, properties, body):
    try:
        task = json.loads(body)
        print(f" [x] Received task {task['id']}")
        
        # Run the sandbox
        result = run_in_sandbox(task['strategy_code'])
        
        # Report success back to orchestrator
        report_result(task['id'], result)
        
        # Acknowledge the message
        ch.basic_ack(delivery_tag=method.delivery_tag)
        
    except Exception as e:
        print(f" [!] Error processing task: {e}")
        # Negative Acknowledge the message, put it back in queue
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=False)
ACK and NACK: Signing for a delivery
When a delivery driver hands you a registered package, you have to sign for it (ACK - Acknowledge). Until you sign, the delivery company considers the package "in transit." If you refuse the package because it's broken, you reject it (NACK - Negative Acknowledge).

In RabbitMQ, if our Python script crashes halfway through a backtest, we never send the ACK. RabbitMQ realizes the worker died and automatically puts the task back on the conveyer belt for another worker to try!

sandbox.py — The Two-Phase Docker Sandbox

Running code generated by an AI is essentially running untrusted, potentially broken, or even malicious code. We cannot run this directly on our host machine. We use Docker to create an isolated "sandbox."

Phase 1: Compilation

The AI writes C++ code (e.g., strategy.cpp). C++ is a compiled language, meaning we must translate the human-readable text into machine code before it can run. We compile this into a Shared Object (.so file) so our C++ engine can load it dynamically.


# sandbox.py snippet
def compile_strategy(source_code_path, output_so_path):
    cmd = [
        "docker", "run", "--rm",
        "-v", f"{source_code_path}:/src/strategy.cpp:ro",
        "-v", f"{output_so_path}:/out",
        "gcc:11",
        "g++", "-O3", "-shared", "-fPIC", "-std=c++20", 
        "/src/strategy.cpp", "-o", "/out/strategy.so"
    ]
    subprocess.run(cmd, check=True)
What does the g++ command mean?
  • g++: The GNU C++ compiler.
  • -O3: "Optimize level 3." This tells the compiler to spend extra time analyzing the code to make the final machine code as blindingly fast as possible (crucial for high-frequency trading).
  • -shared: Build a shared library (like a DLL on Windows) rather than a standalone executable.
  • -fPIC: "Position Independent Code." Required when building shared libraries so the code can be loaded anywhere in memory.
  • -std=c++20: Use the modern C++20 standard, which gives our AI access to the latest language features.
Why compile in a container? If the AI generates a strategy with a weird compiler directive like #include </dev/random>, it could hang the compiler or crash the system. Running the compiler itself inside a container means even the compilation process is sandboxed and secure.

Phase 2: Execution

Once compiled, we run the strategy against our historical tick data.


def run_strategy(so_path, data_path):
    cmd = [
        "docker", "run", "--rm",
        "--network", "none",
        "--memory", "512m",
        "--cpus", "1.0",
        "-v", f"{so_path}:/app/strategy.so:ro",
        "-v", f"{data_path}:/data:ro",
        "backtest-engine"
    ]
    result = subprocess.run(cmd, capture_output=True, text=True)
    
    if result.returncode == 139:
        raise Exception("Segmentation Fault: The AI's code tried to access invalid memory.")
        
    return parse_metrics(result.stdout)
  • --network none: The container has NO internet access. The AI cannot send your data to an external server.
  • --memory 512m and --cpus 1.0: Limits the backtest to half a gigabyte of RAM and 1 CPU core. If the AI writes an infinite loop that eats memory, Docker will kill it before it crashes your server.
  • -v ...:ro: The :ro means Read-Only. The container can read the strategy and the market data, but it cannot modify or delete them.
  • Exit Code 139: In Unix systems, when a program tries to read or write memory it doesn't own, the OS kills it with a "Segmentation Fault" (signal 11). 128 + 11 = 139. If we see 139, we know the AI wrote unsafe C++ pointers!

Cleanup in the finally block

Because we process thousands of AI iterations, left-over files will quickly fill up the hard drive. We wrap our Python execution in a try...finally block.


import shutil

try:
    # Compile and run
    result = process_task()
finally:
    # This ALWAYS runs, even if an exception occurs
    shutil.rmtree(temp_workspace_dir, ignore_errors=True)

SECTION 10: Infrastructure & Docker Compose

Our swarm isn't just one program. It's a database, a message queue, a cache, an orchestrator API, and multiple consumer workers. How do we start all of these without opening 10 terminal windows?

What is Docker Compose?
If Docker is a factory that builds specialized shipping containers, Docker Compose is the orchestra conductor. It reads a single sheet of music (the docker-compose.yml file) and tells all the musicians (the containers) exactly when to start playing, how to talk to each other, and what instruments (volumes/networks) to use. With one command—docker-compose up—the entire symphony starts perfectly.

docker-compose.yml Explained


version: '3.8'

services:
  rabbitmq:
    image: rabbitmq:3-management
    ports:
      - "5672:5672"
      - "15672:15672"
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:alpine
    ports:
      - "6379:6379"

  mongodb:
    image: mongo:latest
    volumes:
      - mongo_data:/data/db

  orchestrator:
    build: ./orchestrator
    ports:
      - "8000:8000"
    environment:
      - RABBITMQ_URL=amqp://rabbitmq
      - MONGO_URL=mongodb://mongodb
    depends_on:
      rabbitmq:
        condition: service_healthy
      mongodb:
        condition: service_started

  worker:
    build: ./worker
    deploy:
      replicas: 3
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - tick_data:/app/data:ro
    environment:
      - RABBITMQ_URL=amqp://rabbitmq
    profiles:
      - full

volumes:
  mongo_data:
  tick_data:
  • rabbitmq: We use the 3-management image because it includes a nice web UI on port 15672 to see our queues. Port 5672 is the actual queue protocol.
  • healthcheck: Why does this matter? If the orchestrator starts before RabbitMQ is ready to accept connections, the orchestrator will crash. The healthcheck tells Docker Compose how to ping RabbitMQ to prove it is fully booted.
  • mongodb: We mount a volume called mongo_data. If we didn't do this, every time we stopped Docker, all our stored AI backtest results would be permanently deleted! Volumes provide persistent storage.
  • orchestrator: Notice depends_on. It waits for RabbitMQ to be healthy (based on the healthcheck) before starting.
  • worker:
    • replicas: 3 starts 3 identical consumer instances automatically!
    • /var/run/docker.sock:/var/run/docker.sock is a technique called "Docker-in-Docker" (or sibling containers). The worker container needs to be able to spawn new sandbox containers for the backtests. By sharing the host's Docker socket, the worker can command the host's Docker engine.
    • profiles: - full: This means workers don't start by default. You have to run docker-compose --profile full up to start them. Great for local UI development when you don't want heavy C++ compilers running.

Worker Dockerfile — Multi-stage Build

What is a multi-stage build?
Imagine you are building a custom car. First, you build a massive factory with cranes, welding machines, and robots. You build the car inside the factory. If you shipped the whole factory to the customer, it would be enormous! Instead, a multi-stage build lets you build the car in the factory (Stage 1), and then drive only the finished car out into a tiny, lightweight transport truck (Stage 2). 

# STAGE 1: Builder
FROM python:3.11-slim as builder
WORKDIR /app
COPY requirements.txt .
# Install compilers and build tools just to compile C/Python dependencies
RUN apt-get update && apt-get install -y gcc
RUN pip wheel --no-cache-dir --no-deps --wheel-dir /app/wheels -r requirements.txt

# STAGE 2: Runtime
FROM python:3.11-slim
WORKDIR /app
# Copy ONLY the pre-built wheels from the builder stage
COPY --from=builder /app/wheels /wheels
RUN pip install --no-cache /wheels/*

COPY . .

# Security: Create a non-root user
RUN useradd -m sandbox_user
USER sandbox_user

CMD ["python", "main.py"]

By discarding the gcc compiler from the final image, our Docker image is hundreds of megabytes smaller and much more secure (if a hacker gets into the container, they don't have a compiler to build malware!). The USER sandbox_user command ensures the application runs with standard, restricted permissions instead of as the all-powerful root.

SECTION 11: Security Model — Protecting Against Malicious AI Code

When you build a system where an AI agent writes C++ code and your server immediately compiles and executes it, you are building an automated malware execution factory if you aren't careful. What if the AI hallucinates and writes a script that deletes files, mines cryptocurrency, or attacks your database?

We use a Defense in Depth approach, consisting of 6 layers.

Layer 1: Network Isolation

The Threat: The AI writes code to download a payload from the internet, or exfiltrate your proprietary trading data to an external server.
The Fix: --network=none when running the Sandbox container. The container has absolutely no network stack. It cannot ping Google, it cannot talk to the host, it cannot reach the database. It is entirely deaf and mute to the network.

Layer 2: Resource Limits

The Threat: The AI writes an infinite while(true) loop, or allocates gigabytes of arrays until the server runs out of memory and crashes (a Denial of Service).
The Fix: Docker cgroups enforce limits: --cpus="1.0" --memory="512m". If the AI code exceeds 512MB of RAM, the Linux kernel instantly terminates the process with an OOM (Out Of Memory) Kill. Your host machine remains perfectly stable.

Layer 3: User Isolation

The Threat: The AI code attempts to modify system configurations inside the container.
The Fix: By specifying USER sandbox_user, the code runs without root privileges. It cannot install software or change core system files, even within its own sandbox.

Layer 4: Timeout Enforcement

The Threat: A bug in the AI's logic causes the backtest to pause and wait for input that will never come, locking up a consumer worker forever.
The Fix: The Python subprocess.run(..., timeout=30) call wraps the Docker execution. If the backtest takes longer than 30 seconds, Python violently terminates the Docker container.

Layer 5: Ephemeral Containers

The Threat: A malicious script writes a backdoor into the filesystem, hoping to affect future backtests.
The Fix: The --rm flag in Docker means the instant the backtest finishes (or fails), the entire container and its filesystem are permanently deleted into the void. The next backtest starts in a pristine, brand-new universe.

Layer 6: Read-Only Mounts

The Threat: The AI tries to tamper with the historical tick data file to cheat the backtest, or tries to overwrite the Python code of the worker.
The Fix: The volumes are mounted with :ro (Read-Only). -v ./data:/data:ro. If the C++ code attempts std::ofstream file("/data/tick.bin");, the operating system denies permission.

SECTION 12: Data Pipeline

A backtester is only as good as the data it processes. In quantitative finance, we process Tick Data.

What is Tick Data?
Most people are used to viewing stock charts in "candles" (e.g., a 1-minute candle shows the open, high, low, and close prices for that minute). Tick data is the raw, unaggregated firehose. Every single time a trade occurs, or a buyer/seller changes their price, a "tick" is recorded.
  • Bid: The highest price a buyer is currently willing to pay.
  • Ask: The lowest price a seller is currently willing to accept.
  • Last: The price of the actual last completed trade.
  • Volume: How many shares were traded.

Generating Synthetic Data

To test our engine, generate_sample_data.py creates realistic synthetic data using geometric Brownian motion (a mathematical model for stock prices). It generates millions of ticks with tiny microsecond timestamps and realistic bid-ask spreads.

Ingesting Data and Apache Arrow

When loading real data from an exchange (usually huge CSV files), parsing text takes too long. Our script ingest_ticks.py reads the CSV once and converts it into Apache Arrow format.

What is Apache Arrow?
Arrow is a columnar memory format. Instead of saving data row-by-row (Timestamp1, Price1, Volume1, Timestamp2, Price2, Volume2), it saves it column-by-column (Timestamp1, Timestamp2... Price1, Price2...). This makes it vastly faster for our C++ engine to perform math on entire arrays of prices at once!

Content Hashing

To save database space, if the AI generates the exact same C++ code twice, we shouldn't run the backtest again. We create an MD5 hash of the source code. If we see a hash we've already computed, we instantly return the cached results. Deduplication saves immense computing power.

SECTION 13: Performance Deep Dive

In quantitative trading, backtesting speed dictates research speed. If a backtest takes 10 minutes, you can test 6 ideas an hour. If it takes 10 milliseconds, you can test 360,000 ideas an hour. We optimized this engine to the absolute limits of modern hardware.

Memory-Mapped I/O vs Traditional File Reading

Normally, when a program reads a file, it calls read(), and the Operating System copies data from the hard drive, into the OS kernel memory, and then copies it again into the application's memory. This double-copy is slow.

We use Memory-Mapped I/O (mmap). We tell the OS, "Treat this file on the hard drive as if it were a giant array in my RAM." The OS handles paging the data directly from the SSD into the application. This achieves Zero-copy reads. The data goes straight from the NVMe drive to the CPU.

SoA vs AoS (Memory Layout)

AoS (Array of Structures): Like a standard list of objects in Python. [ {price, volume}, {price, volume} ]. In RAM, this looks like P V P V P V.
SoA (Structure of Arrays): Like Apache Arrow. { prices: [], volumes: [] }. In RAM, this looks like P P P V V V.

Why does SoA matter? The CPU reads memory in "Cache Lines" (chunks of 64 bytes). If we want to calculate the average price, using AoS means we pull 64 bytes into the CPU, but half of it is Volume data we don't need right now! With SoA, a 64-byte chunk contains only Prices. The CPU cache is utilized 100% efficiently.

SIMD (Single Instruction, Multiple Data)

Modern CPUs have ultra-wide registers. Normally, an addition instruction adds one number to another. SIMD instructions (like AVX2 on Intel) can load 8 distinct 32-bit float prices into a single register and calculate the moving average of all 8 in a single hardware clock cycle. By combining SoA layout with the -O3 compiler flag, the C++ compiler automatically vectorizes the AI's logic, granting a massive 4x to 8x speedup over standard code.

Batch Processing

We process ticks in batches of 4096. Why 4096? A standard memory page in Linux is 4096 bytes. Aligning our processing loops to the hardware page size minimizes TLB (Translation Lookaside Buffer) misses in the CPU, ensuring the processor never has to wait for RAM to catch up.

SECTION 14: End-to-End Walkthrough

Let’s trace the entire lifecycle of a single request through the swarm:

  1. The Spark: The user types "Create a mean-reverting strategy using Bollinger Bands" in the React UI and clicks Execute.
  2. The API Request: The browser sends a JSON POST request to the Python Orchestrator API (FastAPI).
  3. The Brain: The Orchestrator routes the prompt to LangChain. LangChain queries the LLM (like GPT-4), injecting context about our C++ engine's API structure.
  4. Code Generation: The LLM responds with raw C++ code. The Orchestrator extracts the code and assigns it a unique Task ID (e.g., TASK-992).
  5. The Queue: The Orchestrator packages the C++ code into a JSON payload and pushes it to RabbitMQ. It immediately replies to the React UI: "Task accepted, ID: 992."
  6. The Pickup: A Consumer worker, sitting idle, receives TASK-992 from RabbitMQ.
  7. The Sandbox: The worker writes the C++ code to a temporary folder and commands Docker to start the compiler container. 2 seconds later, strategy.so is produced.
  8. The Crucible: The worker mounts strategy.so and 10 years of tick data into a locked-down execution container. The C++ engine fires up, memory-maps the data, and blasts through 50 million ticks in 400 milliseconds.
  9. The Results: The C++ engine prints a JSON string containing the final P&L, Sharpe Ratio, and trade logs to stdout. The worker captures this output.
  10. Storage: The worker updates MongoDB, saving the metrics under TASK-992.
  11. Completion: The worker sends an ACK to RabbitMQ, marking the task as done.
  12. The Reveal: The React UI, which has been polling the API every second, fetches the updated MongoDB document and renders beautiful, glowing green charts showing the backtest results.

SECTION 15: Glossary

  • ACK (Acknowledgement): A signal sent to a message queue confirming a task was successfully completed.
  • Apache Arrow: A high-performance columnar memory format used for fast data analytics.
  • AoS (Array of Structures): A memory layout where fields of an object are stored sequentially.
  • Backtest: Simulating a trading strategy on historical data to see how it would have performed.
  • Consumer: A worker process that listens to a message queue and processes incoming tasks.
  • CRDT (Conflict-free Replicated Data Type): A data structure used in distributed systems that can be updated simultaneously across different computers without conflicts.
  • Docker: A tool that packages software into standardized, isolated containers.
  • Glassmorphism: A UI design trend featuring translucent, blurred, glass-like elements.
  • LangChain: A framework for developing applications powered by language models, allowing AI to chain thoughts and use tools.
  • Message Queue: A middleman service (like RabbitMQ) that holds tasks in a line until workers are ready to process them.
  • Memory-Mapped I/O (mmap): A technique where a file on a hard drive is mapped directly into RAM, allowing incredibly fast access.
  • NACK (Negative Acknowledgement): A signal to a message queue that a task failed and should be retried.
  • Orchestrator: The central brain of a distributed system that manages state, delegates tasks, and routes API requests.
  • Prefetch Count: A setting in RabbitMQ defining the maximum number of unacknowledged messages a consumer can hold.
  • React: A JavaScript library for building user interfaces using reusable components.
  • Sharpe Ratio: A financial metric that measures risk-adjusted return. A higher number means better performance for the amount of risk taken.
  • SIMD (Single Instruction, Multiple Data): A hardware feature allowing a CPU to perform the same operation on multiple data points simultaneously.
  • SoA (Structure of Arrays): A memory layout where all elements of a single field (like all prices) are stored consecutively, maximizing CPU cache efficiency.
  • Tick Data: The most granular level of market data, recording every single trade and quote update.
  • Vite: A modern, lightning-fast build tool and development server for web applications.
  • Zero-copy: A computer operation where the CPU does not perform the task of copying data from one memory area to another, saving processing time.
