1. Executive Summary

This project is an autonomous AI-powered quantitative trading research platform. It uses large language models (LLMs) to automatically:

  1. Ideate a trading strategy hypothesis from a natural language prompt
  2. Generate production-grade C++ code implementing that strategy
  3. Compile the C++ code on-the-fly inside a Docker sandbox
  4. Backtest the strategy against millions of historical market ticks at microsecond latency
  5. Evaluate the results against risk KPIs (Sharpe Ratio, Max Drawdown, Latency)
  6. Self-correct by feeding failures back to the AI coder in a reflection loop

The Core Innovation

Most backtesting frameworks are either fast but manual (C++ engines where humans write every strategy) or AI-powered but slow (Python-based LLM tools with toy backtesting). This project combines both: an AI brain (LangGraph multi-agent orchestrator) generates strategies, while a high-performance C++ engine (with AVX2 SIMD and Apache Arrow) executes them at 2,000,000+ ticks per second.

2. Why Each Technology Was Chosen

2.1 Why Apache Arrow?

Problem: Financial tick data is massive. A single day of SPY tick data can be 50+ million rows. Loading this row-by-row is extremely slow.

FeatureBenefit
Columnar formatFields (bid, ask, last, volume) are stored in contiguous arrays. The CPU only loads the columns it needs.
Memory-mapped I/OArrow files are mmap()-ed directly from disk. The OS pages data on-demand — no explicit read/parse step.
Zero-copyColumnarTickStore reads raw pointers directly from Arrow's buffers (raw_values()). Literally zero data copying.
Language-agnosticPython generates the .arrow file; C++ reads it. No serialization overhead.
Cache-friendlyIterating bid[0], bid[1], bid[2]... hits sequential memory, maximizing L1/L2 cache utilization.

2.2 Why Redis?

Problem: The orchestrator needs fast, ephemeral state storage that persists across agent iterations.

FeatureBenefit
Sub-millisecond latencyAgent state lookups happen inside the LLM prompt-building loop. Redis responds in <1ms.
Sliding window listsAgentMemoryCache uses Redis lists (RPUSH + LTRIM) for bounded iteration history.
TTL expirationAll keys expire after 24 hours. Old sessions clean themselves up.
Pub/Sub for CRDT syncIn multi-node deployments, broadcasts CRDT state changes for conflict-free convergence.

2.3 Why RabbitMQ?

Problem: The orchestrator needs to dispatch C++ jobs to workers across many machines with reliable delivery.

FeatureBenefit
Durable queuesTasks persist on disk. Worker crashes don't lose tasks.
Direct exchange routingCleanly separates request (backtest.task) and response (backtest.result) channels.
Prefetch = 1Fair work distribution — slow workers don't block others.
Manual ACK/NACKPrevents silent data loss on failures.
Horizontal scalingdocker compose up --scale consumer=10 — RabbitMQ handles load-balancing.

2.4 Why LangGraph?

Problem: Strategy generation requires a multi-step, cyclic workflow (research → code → evaluate → reflect → re-code).

FeatureBenefit
StateGraphWorkflow defined as a directed graph with typed state. Each node returns partial updates.
Conditional edgesshould_reflect() decides: loop back to coder or terminate.
Immutable stateiteration_log uses operator.add for append-only semantics.
ComposabilityEach agent is a standalone function — testable, swappable, extensible.

2.5 Why C++ for the Backtesting Engine?

FeatureBenefit
Raw pointer accessNo GC, no reference counting. Direct memory access to Arrow buffers.
AVX2 SIMDProcesses 4 doubles simultaneously for Sharpe ratio and variance calculations.
dlopen() plugin systemAI-generated strategies compiled to .so and loaded at runtime. No interpreter overhead.
Deterministic latencyNo GC pauses. Per-tick latency measured in microseconds.

2.6 Why MongoDB?

Approved strategies need persistent storage. Document storage is a natural fit for heterogeneous records (nested hypotheses, variable metrics, raw C++ source).

2.7 Why Docker for Sandboxing?

FeatureBenefit
network=noneZero network access. Cannot exfiltrate data.
Resource limits0.5 CPU, 512MB RAM. Runaway strategies can't DoS the host.
Non-root userRuns as sandbox (UID 1000), not root.
Ephemeral containersFresh container per backtest. No state leakage.
Timeout enforcementContainer killed after 5s if it hangs.

4.1 Configuration — config.py

Centralized configuration using Pydantic's BaseSettings. All values set via environment variables or .env file.

4.2 LLM Factory — llm_factory.py

create_llm(settings) → BaseChatModel: Factory function that returns the correct LangChain chat model based on llm_provider. Uses lazy imports — if you're using Groq, the OpenAI package doesn't even need to be loaded.

4.3 State Schema — state.py

SwarmState is a TypedDict that flows through every node in the graph. Key detail: iteration_log uses Annotated[list[str], operator.add] for append-only semantics — each node's log entries accumulate, never overwrite.

4.4 Prompts — prompts.py

Contains the full StrategyInterface.hpp header as a string (injected into the coder's prompt), plus system prompts for all three agents: RESEARCHER_SYSTEM, CODER_SYSTEM, EVALUATOR_SYSTEM.

4.5 The Graph — graph.py

build_graph(settings) → CompiledGraph: Builds StateGraph(SwarmState) with nodes: researcher → coder → evaluator → [conditional: coder | END]. Uses functools.partial to inject settings.

4.6 Researcher Node — nodes/researcher.py

researcher_node(state, settings) → dict: Generates a UUID task_id, invokes LLM with the user's prompt, parses response into StrategyHypothesis (falls back to wrapping raw text), saves to Redis CRDT.

4.7 Coder Node — nodes/coder.py

coder_node(state, settings) → dict: Loads iteration history from Redis, builds prompt with hypothesis + reflection notes + compiler errors, invokes LLM, strips markdown fences from output, saves to Redis.

_strip_fences(text) → str: Removes ```cpp / ``` markers that LLMs sometimes add despite instructions.

4.8 Evaluator Node — nodes/evaluator.py

submit_and_evaluate_node(state, settings) → dict: Publishes C++ code to RabbitMQ, waits for result, checks KPIs (drawdown ≤ 15%, latency ≤ 50µs, Sharpe ≥ 1.0). If approved, saves to MongoDB.

should_reflect(state) → str: Returns "end" if approved or max iterations reached; "coder" to retry.

_wait_for_result(channel, task_id, timeout): Polls RabbitMQ result queue every 250ms until matching result or timeout.

4.9 RabbitMQ Broker — broker/rabbitmq.py

Declares exchange (trading_swarm_exchange), queues (backtest_tasks, backtest_results), and routing keys. All messages use delivery_mode=2 (persistent).

4.10 Redis Cache — broker/redis_cache.py

AgentMemoryCache: Sliding-window iteration history per task (default 10 entries). format_for_prompt() renders history as text for LLM context window.

4.11 CRDT State — broker/crdt_state.py

Three CRDT types for conflict-free distributed state:

  • LWWRegister (Last-Writer-Wins): Stores hypothesis, strategy_source, reflection_notes. Timestamp tiebreaking with node_id fallback.
  • ORSet (Observed-Remove Set): Stores iteration_log. UUID-tagged elements with tombstone removal.
  • GCounter (Grow-only Counter): Stores iteration_counter. Per-node counts merged via max.

SwarmStateCRDT: Redis-backed store with merge_remote(), publish_for_sync() (Pub/Sub broadcast), subscribe_sync() (one-shot peer merge).

4.12 FastAPI Backend — api.py

POST /api/run: Accepts prompt, dataset_id, max_iterations → invokes graph.invoke() → returns JSON result. GET /api/health: Returns status + LLM provider. CORS enabled for local dev.

5. The C++ Worker Engine — Every Function Explained

5.1 StrategyInterface — StrategyInterface.hpp

The contract all AI-generated strategies implement: on_init(), on_market(event) → signals, on_fill(fill), finalize() → metrics. Factory: extern "C" create_strategy() for dlopen().

5.2 ColumnarTickStore — ColumnarTickStore.hpp/.cpp

Memory-maps Arrow IPC file, stores raw const double* pointers to each column in BatchView structs.

  • tick_at(index): Locates batch, reconstructs Tick from column pointers.
  • prefetch_batch(start, count): Issues __builtin_prefetch every 64 elements for cache warmth.
  • locate(index): Finds which batch contains a global index.

5.3 BacktestEngine — BacktestEngine.hpp/.cpp

  • load_strategy(lib_path): dlopen() + dlsym("create_strategy") to load compiled strategy.
  • run(): Main event loop — processes ticks in batches of 4096 with next-batch prefetch. Per-tick: read tick → call strategy → process signals through OMS → deliver fills.
  • finalize_result(): Computes Sharpe (via SimdMetrics), drawdown, return, latency percentiles.

5.4 OrderMatchingSimulator — OrderMatchingSimulator.hpp/.cpp

process_signals(): Queues orders, matches market orders immediately with slippage, checks limit order marketability, applies commission, updates position/cash/equity curve.

5.5 SimdMetrics — SimdMetrics.hpp

  • sum(): AVX2 path processes 4 doubles per _mm256_add_pd instruction.
  • variance(): AVX2 _mm256_fmadd_pd for fused multiply-add of squared differences.
  • compute_sharpe(): Annualized with √(252×390).
  • compute_max_drawdown(): Running peak tracking.

6. The Consumer (Task Runner)

6.1 main.py

Connects to RabbitMQ, listens on backtest_tasks, calls SandboxRunner.run_backtest(), publishes results to backtest_results. Manual ACK/NACK for reliability.

6.2 sandbox.py — Two-Phase Execution

Phase 1 (Compile): Write strategy.cpp → docker run --network none → g++ -O3 -shared -fPIC -std=c++20 → strategy.so

Phase 2 (Execute): docker run --network none --memory 512m --cpus 0.5 → swarm_worker dataset.arrow strategy.so → parse JSON from stdout

Handles: compile_error, runtime_error, timeout, segfault (exit code 139).

12. End-to-End Data Flow

  1. User types "Bollinger Band mean reversion" in React UI → POST /api/run
  2. FastAPI calls graph.invoke()
  3. Researcher asks LLM → returns StrategyHypothesis → saves to Redis
  4. Coder loads history from Redis → asks LLM → returns C++ source → saves to Redis
  5. Evaluator publishes task to RabbitMQ → Consumer receives it
  6. Consumer Phase 1: Compile in Docker (network=none) → strategy.so
  7. Consumer Phase 2: Run in Docker sandbox → ColumnarTickStore mmap → BacktestEngine loop (2M ticks) → SimdMetrics → JSON stdout
  8. Consumer publishes result to RabbitMQ
  9. Evaluator receives result, checks KPIs → if failed, sets reflection notes → should_reflect() returns "coder"
  10. Coder (iteration 2): Receives failure feedback → generates improved C++ → cycle repeats
  11. After approval or max iterations → result returned to FastAPI → JSON to React UI
